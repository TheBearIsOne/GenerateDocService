# Архитектура GenerateDocService

> Русский аналог документа [`architecture.md`](architecture.md). При расхождении смысловым источником считается английская версия; фактические изменения необходимо вносить в оба файла.

## 1. Сводный анализ проекта

`GenerateDocService` — модульный монолит на .NET 10 для синхронной и асинхронной генерации документов.

Кодовая база уже содержит:

- разделение в стиле «чистой архитектуры» (Clean Architecture) между уровнями Domain, Application, Infrastructure, Presentation, Host и Client;
- подключаемые (plugin-style) движки генерации документов с дескрипторами метаданных и реестром времени выполнения — в настоящее время девять движков;
- подключаемые провайдеры парсеров шаблонов с кэшированием скомпилированных шаблонов и выбором парсера, предпочитаемого движком;
- синхронный и асинхронный потоки обработки;
- передачу как текстовых, так и двоичных (base64) данных, что делает движки для файлов Office доступными через HTTP;
- абстракции дедупликации запросов и кэширования созданных артефактов;
- долговременное хранение задач на EF Core и PostgreSQL с отправкой через Outbox и применением миграций под блокировкой advisory lock;
- переключаемые инфраструктурные провайдеры: in-memory либо Redis, in-memory либо RabbitMQ, in-memory либо MinIO/объектное хранилище, in-memory либо PostgreSQL;
- аутентификацию по JWT-bearer с ролевыми политиками авторизации;
- настраиваемые ограничения валидации запросов;
- ограниченное число повторов генерации с предельным сроком обработки, а также стандартный конвейер устойчивости HTTP для внешнего конвертера FOP;
- хранение артефактов с ограниченным сроком и очистку, включая перевод задач, покинутых в состоянии `Processing`, в `Failed`;
- проверки работоспособности, распространение идентификаторов корреляции, логирование, трассировку, метрики, интеграционные тесты, базовые оценки производительности NBomber и микробенчмарки BenchmarkDotNet внутри процесса.

Это уже не заготовка, а рабочая основа сервиса с рядом решений, ориентированных на промышленную эксплуатацию. Первая фаза `docs/improvement-plan.md` (персистентность, валидация, аутентификация, устойчивость) завершена; раздел 9 перечисляет то, что по-прежнему не позволяет заявлять о полной готовности к промышленной эксплуатации.

## 2. Структура решения

## 2.1 Основные модули

- `src/Modules/DocumentProcessing/GenerateDocService.DocumentProcessing.Domain`
  - базовое состояние задач и доменные понятия;
- `src/Modules/DocumentProcessing/GenerateDocService.DocumentProcessing.Application`
  - оркестрация, реестры, сервисы, абстракции, контракты сообщений, абстракции кэширования;
- `src/Modules/DocumentProcessing/GenerateDocService.DocumentProcessing.Infrastructure`
  - внедрение зависимостей, интеграции с Redis/MinIO/RabbitMQ/PostgreSQL, проверки работоспособности, регистрация движка `fake`;
- `src/Modules/DocumentProcessing/GenerateDocService.DocumentProcessing.Presentation`
  - HTTP-контракты и сопоставление ответов.

## 2.2 Узлы и клиенты

- `src/Host/GenerateDocService.Api`
  - узел minimal API, промежуточное ПО, JWT-аутентификация и политики авторизации, OpenTelemetry, Serilog, эндпоинты проверок работоспособности;
- `src/Host/GenerateDocService.Worker`
  - выделенный узел фоновой обработки; выполняет потребитель MassTransit независимо от HTTP-трафика и использует те же уровни Application и Infrastructure, поэтому API и воркер масштабируются раздельно;
- `src/Clients/GenerateDocService.SampleClient`
  - демонстрационный клиент с интерактивным меню по всем доступным движкам и размещёнными микробенчмарками BenchmarkDotNet в каталоге `Benchmarks/`.

## 2.3 Движки

- `src/Engines/GenerateDocService.Engine.Abstractions`
  - контракты движков и парсеров, атрибуты метаданных, дескрипторы, а также `NonRetryableGenerationException`;
- `src/Engines/GenerateDocService.Engine.Scriban`
  - движок генерации и парсер шаблонов на базе Scriban;
- `src/Engines/GenerateDocService.Engine.DotLiquid`
  - движок генерации и парсер шаблонов на базе DotLiquid;
- `src/Engines/GenerateDocService.Engine.QuestPdf`
  - генерация PDF из JSON средствами QuestPDF;
- `src/Engines/GenerateDocService.Engine.MiniExcel`
  - генерация XLSX и заполнение шаблонов средствами MiniExcel;
- `src/Engines/GenerateDocService.Engine.MiniWord`
  - заполнение шаблонов DOCX средствами MiniWord;
- `src/Engines/GenerateDocService.Engine.MiniPdf`
  - преобразование DOCX/XLSX в PDF;
- `src/Engines/GenerateDocService.Engine.Fop`
  - HTTP-адаптер преобразования FO/XSL-FO в PDF через внешний сервис FOP Converter API;
- `src/Engines/GenerateDocService.Engine.Api`
  - настраиваемое обобщение движка `fop`: отправляет полезную нагрузку методу POST именованного внешнего HTTP-сервиса и возвращает тело ответа как документ. Целевые сервисы и их учётные данные задаются в конфигурации, а не в данных запроса.

Девятый движок, `fake`, регистрируется из каталога `GenerateDocService.DocumentProcessing.Infrastructure/Engines/`, а не из собственного проекта; он существует для smoke-проверок и как резервный вариант маршрутизации.

## 2.4 Тесты

- `tests/Unit/GenerateDocService.DocumentProcessing.Application.Tests`
  - сохраняет проверяемый результат каждого внутрипроцессного движка в `artifacts/test-results/<engine>/`;

  - нормализует префиксный SpreadsheetML, созданный MiniExcel, перед преобразованием в MiniPdf, чтобы значения ячеек отображались;
  - покрывает классификацию повторов и задержку, ограничения TTL и объёма для провайдеров в памяти, очистку артефактов и регистрацию DI для устойчивости;
- `tests/Integration/GenerateDocService.Api.IntegrationTests`
  - выполняет необязательный тест преобразования XSL-FO/XML-шаблона Scriban через конвертер FOP, если задана переменная `FOP_CONVERTER_BASE_URL`, и записывает полученный PDF в `artifacts/test-results/fop/`;
  - размещает `MockApiService` — реальный сервис на Kestrel, используемый для проверки движка `api` по всем схемам аутентификации, а также по пути без аутентификации;
  - содержит тесты с тегом `Category=RequiresDocker`, которые запускают реальные контейнеры PostgreSQL, RabbitMQ, Redis и MinIO через Testcontainers и корректно пропускаются, когда демон Docker недоступен;
- `tests/Performance/GenerateDocService.LoadTests.NBomber`
  - профили сквозной нагрузки через HTTP; компонентный аналог размещён в клиентском приложении.

## 3. Архитектурный стиль

Сервис сочетает:

- «чистую архитектуру» (Clean Architecture);
- модульный монолит;
- подключаемую архитектуру (Plugin Architecture) для движков и парсеров шаблонов;
- событийно-ориентированную асинхронную обработку.

### 3.1 Ответственность уровней

#### Domain
Содержит понятия жизненного цикла задач и переходы состояний.

#### Application
Содержит оркестрацию и всю бизнес-логику рабочих процессов:

- выбор движка;
- синхронная генерация;
- постановка асинхронной задачи;
- фоновая обработка;
- дедупликация;
- кэширование артефактов;
- переходы состояний задач;
- регистрация метрик.

#### Infrastructure
Содержит технические адаптеры и переключение провайдеров:

- регистрация внедрения зависимостей, включая выбор провайдера через `services.Replace(...)`;
- реализации кэша и дедупликации на Redis;
- ограниченные реализации кэша и дедупликации в памяти с TTL и лимитом объёма;
- хранилище артефактов на MinIO;
- интеграция с шиной MassTransit и диспетчер Outbox на PostgreSQL;
- персистентность на EF Core и PostgreSQL, миграции и применение схемы при запуске под блокировкой advisory lock;
- `ArtifactRetentionCleaner` (политика очистки) и `ArtifactCleanupBackgroundService` (только её планировщик);
- регистрация устойчивости: параметры повторов генерации, `TransientFailureClassifier` и стандартный обработчик устойчивости для `HttpClient` конвертера FOP;
- регистрация и проверка целей движка `api`, которая аварийно завершает запуск вместо сбоя при первом запросе;
- проверки работоспособности;
- сканирование сборок для движков и парсеров шаблонов.

#### Presentation
Содержит контракты API и логику сопоставления ответов. Валидация запросов и политики авторизации намеренно здесь **не** размещаются — это ответственность узла: `src/Host/GenerateDocService.Api/Validation` и `.../Security`.

#### Host
Содержит транспортную обвязку:

- HTTP-эндпоинты;
- промежуточное ПО;
- ограничения валидации запросов (`GenerateDocumentRequestValidator`, применяется как фильтр эндпоинта);
- JWT-аутентификация и ролевые политики авторизации, применяемые условно через `MaybeRequireAuth`;
- логирование;
- трассировка;
- экспорт метрик;
- OpenAPI и интерфейс Scalar, включаемые через `DocumentProcessing:Api:ExposeOpenApi`.

### 3.2 Модель отказоустойчивости

В конструкцию изначально заложено несколько шаблонов устойчивости, которые сохраняют работоспособность задач генерации при временных сбоях:

- фоновая генерация повторяет временные сбои с экспоненциальной задержкой до достижения настроенного предельного срока. `TransientFailureClassifier` определяет, что считать временным сбоем: по умолчанию это `HttpRequestException`, `TimeoutException`, `IOException` и `SocketException`, а при включённом провайдере Redis дополнительно `RedisConnectionException`. Классификатор проходит всю цепочку вложенных исключений;
- движок может **исключить** сбой из повторов, выбросив `NonRetryableGenerationException`. Классификатор проверяет это исключение раньше любого типа временного сбоя и на каждом уровне цепочки, поэтому отказ всегда имеет приоритет. Так поступает движок `api`: настроенный целевой сервис — неизвестная третья сторона, чьи эндпоинты могут не быть идемпотентными, а запрос мог быть принят ещё до появления ошибки, поэтому автоматический повтор способен продублировать побочный эффект. `fop` — противоположный случай: его конвертер идемпотентен, поэтому он сохраняет и конвейер устойчивости HTTP, и повторы процесса обработки;
- отмена всегда окончательна. Истёкший предельный срок обработки не приводит к ещё одной полной попытке, а событие `DocumentGenerationFailed` публикуется один раз после последней попытки, а не на каждом повторе;
- паттерн Outbox на PostgreSQL и аренда задачи гарантируют, что асинхронная работа не теряется при перезапуске API или воркера; дублирующая доставка допускается конечным автоматом состояний задачи;
- конвертер FOP использует стандартный обработчик устойчивости `HttpClient` с таймаутом попытки, общим таймаутом, окнами повторов и предохранителем (circuit breaker), поэтому отказы конвертера не приводят к неограниченному ожиданию. `HttpStandardResilienceOptions` требует, чтобы окно выборки покрывало не менее двух таймаутов попытки, а общий бюджет — все попытки; регистрация автоматически расширяет оба значения, поэтому отредактированная вручную конфигурация не может превратить первый запрос в `OptionsValidationException`;
- `ArtifactRetentionCleaner` переводит задачи, оставшиеся в состоянии `Processing` дольше `StuckProcessingTaskSeconds`, в `Failed`, поэтому аварийно завершившийся воркер не может оставить клиента в бесконечном опросе или закрепить отпечаток за задачей, которая никогда не завершится;
- кэши готовых документов и дедупликации запросов уменьшают объём повторяемой работы и помогают системе восстанавливаться после временных дублирующих отправок, не выполняя одну и ту же задачу многократно;
- провайдеры в памяти применяют TTL и ограничение объёма, поэтому локальная разработка остаётся безопасной под нагрузкой и не приводит к неограниченному росту потребления памяти;
- проверки работоспособности охватывают готовность движков и каждого выбранного инфраструктурного провайдера, поэтому эксплуатационные проблемы видны до того, как затронут запросы пользователей.

Это ещё не полная модель отказоустойчивости распределённой системы, но уже прочная основа для модульного монолита, которая даёт проекту практический путь к более промышленному развертыванию. Раздел 9 перечисляет оставшиеся пробелы — прежде всего отсутствие политик для самих клиентов Redis, RabbitMQ и MinIO, а также отсутствие изоляции (bulkhead) и ограничения частоты запросов для параллельной генерации.

## 4. Основные строительные блоки

## 4.1 Подсистема движков

Подсистема движков — одна из наиболее сильных частей конструкции.

Ключевые элементы:

- `IDocumentGenerationEngine`
- `DocumentEngineAttribute`
- `DocumentGenerationEngineDescriptor`
- `DocumentGenerationEngineRegistry`

Поведение:

- движки обнаруживаются сканированием сборок;
- регистрируются только движки, помеченные атрибутом;
- дескрипторы раскрывают поддерживаемые форматы входных данных, результатов и шаблонов, а также приоритет;
- реестр умеет выполнять разрешение по имени и поиск кандидатов по возможностям;
- если поле `engine` в запросе отсутствует, выбирается подходящий движок с наивысшим приоритетом, а при равенстве приоритетов — первый по имени (по возрастанию).

### Текущие возможности и приоритеты движков

Таблица получена из атрибутов `[DocumentEngine]`, то есть описывает фактическую таблицу маршрутизации реестра:

| Движок | Вход | Результат | Шаблон | Приоритет |
|--------|------|-----------|--------|-----------|
| `api` | любой | любой | — | 10 |
| `fake` | json, xml, csv, html, markdown | txt, json, html | scriban, liquid, html, markdown | 0 |
| `dotliquid` | json | txt, html, json, md, markdown | liquid, dotliquid, txt, html, md, markdown | 90 |
| `scriban` | json | txt, html, json, md, markdown | scriban, txt, html, md, markdown | 100 |
| `miniword` | json | docx | miniword, docx | 100 |
| `miniexcel` | json | xlsx | xlsx | 150 |
| `questpdf` | json | pdf | json, txt, html, md, markdown | 200 |
| `minipdf` | docx, xlsx | pdf | — | 250 |
| `fop` | fo, xsl-fo | pdf | — | 300 |

Два следствия из этой таблицы стоит сформулировать явно:

- **`api` не объявляет форматов.** Его возможности определяются конфигурацией, а не метаданными, поэтому он регистрируется с пустыми массивами, и `/api/v1/engines` выводит его без форматов. Автовыбор при этом корректно находит его, поскольку `CanHandle` обращается к настроенным целям. Его приоритет 10 — наименьший среди реальных движков, поэтому специализированный движок всегда выигрывает, если запрос могут обработать оба: пару `xsl-fo -> pdf` забирает `fop` с приоритетом 300, хотя предварительно настроенная цель `converter` ей также соответствует.
- **Приоритет 0 у `fake` — намеренный нижний предел.** Он соответствует широкому набору форматов, но проигрывает любому реальному движку, поэтому выбрать его можно только явно либо когда больше не подходит ни один движок.

Такая схема делает маршрутизацию движков детерминированной и расширяемой.

## 4.2 Подсистема парсеров шаблонов

Ключевые элементы:

- `ITemplateParser`
- `ITemplateParserRegistry`
- `ICompiledTemplateCache`
- `TemplateParserRegistry`
- `ScribanTemplateParser`
- `DotLiquidTemplateParser`

Поведение:

- движки делегируют разбор шаблона провайдерам парсеров;
- скомпилированные шаблоны кэшируются по хэшу;
- провайдер кэша может быть в памяти либо на Redis;
- реестр парсеров выполняет разрешение парсера по формату шаблона.

Метод `ITemplateParserRegistry.Resolve` принимает необязательный параметр `preferredParserName`, и каждый движок передаёт собственное имя. Это важно, потому что форматы шаблонов пересекаются: и `ScribanTemplateParser`, и `DotLiquidTemplateParser` поддерживают `txt`, `html`, `md` и `markdown`. Без предпочтения спорный формат разрешался в алфавитном порядке, поэтому запрос `engine=scriban` с `templateFormat=html` мог получить компиляцию DotLiquid, которую движок Scriban не способен выполнить, — ошибку HTTP 500. С предпочтением побеждает тот парсер, который действительно может использовать результат. Если предпочтение не задано либо предпочитаемый парсер отсутствует среди кандидатов, сохраняется прежнее алфавитное правило; оно зафиксировано тестом, чтобы его изменение было осознанным.

Стоит знать об одной асимметрии: `RedisCompiledTemplateCache` молча ничего не сохраняет для компиляций DotLiquid, поэтому при провайдере Redis такие шаблоны разбираются заново на каждый запрос. Это поведение закреплено тестом, а не скрыто.

Такое разделение оправдано, поскольку разбор шаблона — отдельная «горячая точка», отличная от самой генерации.

## 4.3 Подсистема асинхронной обработки

Ключевые элементы:

- `AsyncDocumentGenerationService`
- `BackgroundDocumentGenerationProcessor`
- `IBackgroundGenerationScheduler`
- `GenerateDocumentRequested`
- `DocumentGenerated`
- `DocumentGenerationFailed`
- `IDocumentGenerationTaskRepository`
- `GenerationResilienceOptions` и `TransientFailureClassifier`
- `ArtifactRetentionCleaner`

Поведение:

- API принимает асинхронный запрос;
- запрос нормализуется и дополняется метаданными корреляции;
- создаётся отпечаток для дедупликации;
- задача и сериализованное сообщение генерации фиксируются совместно при выборе PostgreSQL;
- диспетчер Outbox на PostgreSQL берёт ожидающие сообщения в аренду и отправляет их через MassTransit;
- сбои отправки повторяются с задержкой и в итоге переводят задачу в `Failed`;
- фоновый процессор выполняет генерацию и сохранение артефакта, повторяя классифицированные временные сбои в пределах предельного срока обработки;
- состояние задачи обновляется, а события жизненного цикла публикуются по возможности — один раз после последней попытки;
- отдельно `ArtifactRetentionCleaner` удаляет завершённые и неуспешные задачи по истечении сроков хранения и переводит задачи, застрявшие в `Processing`, в `Failed`.

Решение о повторе принимается однократным проходом по цепочке исключений в таком порядке: `NonRetryableGenerationException` в любом месте цепочки прекращает повторы, затем отмена прекращает их, затем первый совпавший тип временного сбоя включает повтор. Именно этот порядок позволяет движку наложить вето на повторы для вызова, безопасность повторения побочных эффектов которого он не может гарантировать.

## 4.4 Подсистема кэширования и хранения

Ключевые элементы:

- `IGenerationRequestDeduplicationStore`
- `IGeneratedDocumentCache`
- `IDocumentArtifactStore`
- реализации кэша на Redis;
- реализация хранилища артефактов на MinIO.

Поведение:

- дедупликация предотвращает дублирующую асинхронную работу для одного отпечатка запроса;
- кэш готовых документов способен сократить повторную генерацию;
- хранение артефактов абстрагировано от модели задач.

## 4.5 Использование инфраструктурных технологий

Ни один проект движка не ссылается напрямую на Redis, MinIO или MassTransit и не вызывает их. Движки получают запросы через `IDocumentGenerationEngine` и возвращают результаты; общие сервисы приложения используют абстракции кэширования, хранения и обмена сообщениями. Парсеры шаблонов Scriban и DotLiquid действительно используют `ICompiledTemplateCache`, который может работать на Redis при выборе соответствующего провайдера. Хранилище артефактов MinIO и обмен сообщениями MassTransit остаются вне вызовов движков. Проект Infrastructure регистрирует выбранные реализации для обоих узлов — API и Worker.

Два движка всё же выполняют **исходящие HTTP-вызовы** через `IHttpClientFactory`, а не через созданный вручную клиент: `fop` обращается к внешнему конвертеру, а `api` — к именованной цели, которую разрешает конфигурация. Оба клиента регистрируются в Infrastructure, где и определяется их поведение при сбоях: клиент FOP получает стандартный обработчик устойчивости, а клиенты `api` намеренно не получают никакого, поскольку повтор запроса к неизвестной третьей стороне — это именно то, что призвано предотвращать `NonRetryableGenerationException`.

| Технология | Где используется | Как используется |
|------------|------------------|------------------|
| Redis (`StackExchange.Redis`) | Адаптеры кэширования в Infrastructure | Заменяет `ICompiledTemplateCache`, `IGeneratedDocumentCache` и `IGenerationRequestDeduplicationStore`. Скомпилированные шаблоны и ссылки на готовые документы — кэши «по возможности»: временный сбой кэша трактуется как промах. Резервирование дедупликации запросов остаётся fail-closed, чтобы избежать дублирующей работы между экземплярами. |
| MinIO (клиент `Minio` для .NET) | `MinioDocumentArtifactStore` | Реализует `IDocumentArtifactStore`. Воркер записывает созданные файлы в настроенную корзину по пути `{requestId}/{fileName}`; записи задач хранят полученный путь, а эндпоинт скачивания читает артефакт через ту же абстракцию. |
| MassTransit | Адаптеры обмена сообщениями в Infrastructure | Диспетчер Outbox на PostgreSQL отправляет `GenerateDocumentRequested` в настроенную очередь RabbitMQ. Условная аренда в базе координирует диспетчеры в узлах API/Worker; ожидающие данные очищаются после подтверждения брокером. При персистентности in-memory отправка выполняется напрямую. События жизненного цикла публикуются через `MassTransitDocumentGenerationEventPublisher`. |
| PostgreSQL (`Npgsql` + EF Core) | `PostgreSqlDocumentGenerationTaskRepository`, диспетчер Outbox, миграции | Долговременное состояние задач и ожидающие данные команды, фиксируемые атомарно. Оба узла применяют ожидающие миграции при запуске под блокировкой advisory lock PostgreSQL, поэтому одновременные запуски не конфликтуют по DDL. Метод `GetAsync` использует `AsNoTracking`, поэтому вызывающей стороне, которая добавляет сущность, а затем обновляет её, нужна отдельная область на каждую фазу. |
| Исходящий HTTP (`IHttpClientFactory`) | Движки `fop` и `api` | `fop` отправляет multipart-часть `primaryDocument` внешнему конвертеру через клиент с `AddStandardResilienceHandler`. `api` использует два клиента — один для запросов, один для обмена токенами OAuth2, — и ни один из них не имеет обработчика устойчивости. |

MassTransit намеренно закреплён на версии **8.5.10**. Версия 9 требует платной лицензии, поэтому её обновление — коммерческое решение, а не обычное обновление зависимости; не повышайте её в рамках посторонних задач.

Эти адаптеры не обязательны при каждом запуске. `appsettings.json` и параметры окружения Development по умолчанию выбирают кэширование, обмен сообщениями, хранение и персистентность в памяти. Файл `deploy/docker/docker-compose.yml` настраивает Redis, RabbitMQ через MassTransit, MinIO и PostgreSQL и для API, и для воркера. PostgreSQL хранит состояние задач и ожидающие данные команды атомарно; Redis не заменяет репозиторий задач. Outbox работает по принципу «at-least-once», поэтому потребитель атомарно принимает задачу и игнорирует дублирующие доставки после того, как задача покинула состояние `Queued`.

## 5. Потоки вызовов во время выполнения

## 5.1 Синхронный поток запроса

```text
Client
  -> POST /api/v1/documents/sync
  -> CorrelationIdMiddleware injects correlation metadata
  -> JWT bearer authentication + role policy (when auth is enabled)
  -> ValidationRequestFilter endpoint filter, delegating to GenerateDocumentRequestValidator
       -> size limits measured against the DECODED base64 length
       -> payload/payloadBase64 and template/templateBase64 mutual exclusion
       -> 400 with field-level details on any violation
  -> Program.cs maps HTTP contract to GenerateDocumentRequest, decoding base64 once
  -> SyncDocumentGenerationService
       -> ResolveRequest()
            -> explicit engine OR auto-select by capability/priority
       -> registry.Resolve(engine)
       -> engine.GenerateAsync(request)
            -> template parser registry resolves parser, preferring the engine's own name
            -> compiled template cache may be used
       -> DocumentGenerationMetrics record success/failure
  -> API returns the result stream through Results.File, without copying to a byte[]
```

В синхронном пути повторы **отсутствуют**: сбой возвращается вызывающей стороне, которая сама решает, отправлять запрос повторно. Ограниченные повторы существуют только в фоновом процессоре, где никто не ждёт ответа на соединении.

## 5.2 Асинхронный поток запроса

```text
Client
  -> POST /api/v1/documents/async
  -> Program.cs maps HTTP contract to GenerateDocumentRequest
  -> CorrelationIdMiddleware injects correlation metadata
  -> AsyncDocumentGenerationService
       -> ResolveRequest()
       -> create request fingerprint
       -> reserve dedup entry
      -> persist task and outbox payload together
  -> API returns 202 Accepted + task status payload

    Outbox dispatcher
      -> lease pending outbox row
      -> send GenerateDocumentRequested through MassTransit
      -> clear pending payload after broker acceptance
      -> retry with backoff; mark task Failed after the configured attempt limit

Background consumer/processor
  -> receives GenerateDocumentRequested
  -> BackgroundDocumentGenerationProcessor
       -> load task
       -> mark Processing
       -> check generated document cache by fingerprint
       -> if miss: resolve engine and generate document
       -> save artifact to store
       -> update generated document cache
       -> mark Completed or Failed
       -> publish DocumentGenerated or DocumentGenerationFailed

Client
  -> GET /api/v1/tasks/{taskId}
  -> GET /api/v1/tasks/{taskId}/download
```

Диаграмма последовательности для конфигурации Compose (RabbitMQ, Redis, MinIO и PostgreSQL) находится в файле [async-generation-sequence.mmd](async-generation-sequence.mmd). Документ [асинхронная последовательность MiniExcel](miniexcel-async-sequence-sc.mmd) описывает путь `json -> xlsx`, включая отправку через Outbox и ветви с шаблоном и кэшем. При провайдерах in-memory по умолчанию используются те же абстракции приложения, но без этих внешних сервисов и без Outbox на PostgreSQL.

## 5.3 Поток автоматического выбора

```text
Request without engine
  -> registry.FindCandidateDescriptors(input, output, templateFormat)
  -> order by Priority desc, then Name asc
  -> take first candidate
  -> continue with resolved engine name
```

## 5.4 Поток формирования документа по шаблону

```text
Engine
  -> choose parser from ITemplateParserRegistry, passing its own name as the preference
  -> hash template content
  -> try ICompiledTemplateCache
  -> if miss: compile template and cache it
  -> render against JSON payload model
  -> return GeneratedDocumentResult
```

## 5.5 Выбор целевого сервиса в движке `api`

У движка `api` нет собственных форматов, поэтому маршрутизация к конкретному эндпоинту — это второй шаг разрешения, который выполняется *внутри* движка уже после того, как реестр выбрал сам движок. Метод `ResolveTarget` применяет четыре правила по порядку и выбрасывает исключение вместо молчаливого ухудшения поведения:

```text
1. metadata["api.target"] present and non-empty
     -> target must EXIST          (else InvalidOperationException)
     -> target must MATCH formats   (else InvalidOperationException)
     -> no fall-through to the next rule on failure
2. else DefaultTarget configured
     -> must exist                 (else InvalidOperationException)
     -> returned WITHOUT a format check
3. else first target, ordered by name (OrdinalIgnoreCase), whose declared formats match
4. else InvalidOperationException naming both the metadata key and the DefaultTarget setting
```

Три свойства этого порядка являются намеренными:

- **Именованная цель, не соответствующая форматам, — это ошибка, а не повод для резервного варианта.** Если вызывающая сторона запрашивает `converter`, а `converter` не может обработать `json -> pdf`, движок отказывает вместо того, чтобы незаметно выбрать другой эндпоинт. Молчаливая подмена сделала бы происхождение ответа неподдающимся аудиту.
- **Для `DefaultTarget` проверка форматов пропускается.** Это явное указание оператора «отправлять всё остальное сюда», поэтому оно выполняется как задано. Правила 1 и 3 проверяют форматы, правило 2 — нет. Это единственное место, где несоответствие может дойти до сети, поэтому `DefaultTarget` должен указывать на универсальный эндпоинт.
- **Правило 3 выполняет сортировку по имени**, а не по порядку перечисления словаря, поэтому разрешение детерминировано между запусками и перезагрузками конфигурации.

Метод `Matches` трактует `InputFormat`/`OutputFormat` цели как подстановочные, если они пусты, что позволяет одной цели обслуживать несколько пар форматов.

Разрешение цели является также **границей безопасности** движка: каждая ветвь читает данные из `options.Value.Targets`, поэтому запрос может выбрать цель, но никогда не может передать URL. Это закреплено тестом: настраивается цель, указывающая на link-local адрес метаданных, и проверяется, что запрос завершается ошибкой при нулевом числе обращений к имитационному внешнему сервису, — доказательство того, что именование цели не может перенаправить трафик на произвольный узел.

Сбои оборачиваются в `NonRetryableGenerationException`, кроме отмены: она распространяется дальше, чтобы истёкший предельный срок не был принят за сбой внешнего сервиса.

## 6. Модель конфигурации инфраструктуры

Приложение может работать в облегчённом режиме либо в режиме, приближенном к промышленному. Четыре раздела выбирают провайдера, и у каждого есть значение по умолчанию in-memory, поэтому `dotnet run` работает без какой-либо инфраструктуры.

### 6.1 Выбор провайдера

| Раздел | Значения | Что заменяет |
|--------|----------|--------------|
| `DocumentProcessing:Persistence:Provider` | `InMemory`, `PostgreSql` | `IDocumentGenerationTaskRepository`, а также включает диспетчер Outbox |
| `DocumentProcessing:Caching:Provider` | `InMemory`, `Redis` | `ICompiledTemplateCache`, `IGeneratedDocumentCache`, `IGenerationRequestDeduplicationStore` |
| `DocumentProcessing:Messaging:Transport` | `InMemory`, `RabbitMQ` | Шину MassTransit и потребитель `GenerateDocumentRequested` |
| `DocumentProcessing:Storage:Provider` | `InMemory`, `ObjectStorage` | `IDocumentArtifactStore` (MinIO) |

Выбор выполняется через `services.Replace(...)`, поэтому уровень приложения не узнаёт, какая реализация ему передана. При транспорте `InMemory` планировщик *публикует* сообщение, и MassTransit маршрутизирует его по соглашению; при `RabbitMQ` он *отправляет* его в очередь с именем из `DocumentProcessing:Messaging:QueueName` (по умолчанию `document-generation`), которое должно совпадать с конечной точкой приёма потребителя, иначе сообщения останутся необработанными.

### 6.2 Поведенческие параметры

| Раздел | Назначение |
|--------|------------|
| `DocumentProcessing:Resilience` | `ProcessingTimeoutSeconds` (300), `MaxAttempts` (3), `InitialDelayMilliseconds` (250), `MaxDelayMilliseconds` (5000), `BackoffMultiplier` (2.0) |
| `DocumentProcessing:InMemory` | `GeneratedDocumentTtlMinutes` (60), `MaxCachedDocuments` (1000), `DeduplicationTtlMinutes` (15); значение `0` отключает истечение срока |
| `DocumentProcessing:Retention` | `RetentionDays` (30), `FailedTaskRetentionDays` (7), `StuckProcessingTaskSeconds` (1800), `CleanupIntervalHours` (1) |
| `DocumentProcessing:Validation` | `MaxPayloadSizeBytes` (10 МБ), `MaxTemplateSizeBytes` (5 МБ), `MaxMetadataEntries` (50), `MaxMetadataKeyLength` (128), `MaxMetadataValueLength` (1024), `MaxEngineNameLength` (64), `MaxFormatNameLength` (64), `MaxRequestIdLength` (64) |
| `DocumentProcessing:Fop` | `BaseUrl` конвертера и семь параметров конвейера устойчивости |
| `DocumentProcessing:Authentication` | `Enabled`, `Issuer`, `Audience`, `SigningKey` |
| `DocumentProcessing:Api` | Используется двумя классами параметров — см. ниже |

Раздел `DocumentProcessing:Api` читают **два** несвязанных класса, поскольку оба относятся к HTTP-поверхности: `ApiHostOptions` в узле API (`ExposeOpenApi`, `ExposeHealthDetails`) и `DocumentProcessingApiOptions` в движке `api` (`Targets`, `DefaultTarget`). Они привязывают разные ключи одного раздела, поэтому добавление ключа в любой из них безопасно, но об общем имени стоит знать до поиска по коду.

### 6.3 Целевые сервисы движка `api`

Цели задаются в конфигурации, а не в данных запроса. Запрос может лишь *назвать* предварительно настроенную цель через ключ метаданных `api.target`, поэтому движок невозможно превратить в открытый прокси, а секрет никогда не передаётся в теле запроса. Метод `DocumentProcessingApiOptions.Validate()` выполняется при регистрации, поэтому некорректная цель — относительный `BaseUrl`, пустой `RequestPath`, цель со схемой `Basic` без учётных данных, `DefaultTarget`, указывающий на несуществующую цель, — приводит к сбою узла при **запуске**, а не при первом запросе.

Каждая цель объявляет `BaseUrl`, `RequestPath` (с подстановкой `{requestId}`/`{correlationId}`), `Method`, `ContentType`, необязательное поле `MultipartFieldName`, необязательные `InputFormat`/`OutputFormat`, `TimeoutSeconds` и блок `Authentication`, у которого `Scheme` принимает значение `None`, `Basic`, `Bearer` или `OAuth2ClientCredentials`.

### 6.4 Локальный docker-стек

Файл `deploy/docker/docker-compose.yml` запускает:

- API и Worker
- RabbitMQ
- Redis
- MinIO
- PostgreSQL

Стек настраивает и API, и воркер на использование этих внешних провайдеров и работает с `ASPNETCORE_ENVIRONMENT=Production`. Инфраструктурные порты привязаны к `127.0.0.1`, API публикуется на порту узла **8081** (порт контейнера 8080), а Redis — на **6380** (порт контейнера 6379), чтобы стек мог работать параллельно с отдельным проектом `fopconverter`, который занимает 8080 и 6379. Контейнеры по-прежнему обращаются друг к другу по имени сервиса через внутреннюю сеть, поэтому переназначение действует только на стороне узла.

В стеке включена аутентификация, поэтому ключ `GDS_AUTH_SIGNING_KEY` необходимо передать через `deploy/docker/.env`; при его отсутствии compose завершается аварийно. Конвертер FOP не входит в этот compose-файл и настраивается отдельно через `FOP_CONVERTER_BASE_URL`, по умолчанию `http://host.docker.internal:8080/`, поскольку `localhost:8080` внутри контейнера — это сам контейнер.

### 7.3 Метрики

Формируются из источника метрик `GenerateDocService.DocumentProcessing`:

- `document_generation_sync_requests_total`
- `document_generation_async_requests_total`
- `document_generation_completed_total`
- `document_generation_failed_total`
- `document_generation_duration_ms`

Каждый инструмент несёт теги `engine` и `output_format`. Длительность регистрируется и на пути успешного завершения, и на пути сбоя, поэтому сбой всё же даёт выборку задержки, а не исчезает из гистограммы.

Отметим, чего эти счётчики **не** показывают: `document_generation_failed_total` регистрируется один раз на задачу, после последней попытки, а не на каждую попытку. Задача, израсходовавшая три повтора, увеличивает счётчик сбоев один раз — точно так же, как задача, упавшая немедленно. Давление повторов видно в `document_generation_duration_ms`, а не в числе сбоев; именно так и был впервые замечен отсутствующий отказ от повторов у движка `api` — как длительность 13 секунд для внешнего сервиса, который просто отклонял соединения.

### 7.4 Проверки работоспособности

Регистрации помечены тегами, а `/health/live` и `/health/ready` фильтруют по этим тегам:

| Проверка | Теги | Когда регистрируется |
|----------|------|----------------------|
| `document-engines` | live, ready | всегда |
| `authentication` | live, ready | всегда |
| `redis-cache` | ready | провайдер кэширования Redis |
| `cache-provider` | live, ready | провайдер кэширования в памяти |
| `postgresql-persistence` | ready | провайдер персистентности PostgreSQL |
| `task-persistence` | live, ready | провайдер персистентности в памяти |
| `rabbitmq-transport` | ready | транспорт RabbitMQ |
| `messaging-transport` | live, ready | транспорт в памяти |
| `object-storage` | ready | провайдер MinIO/объектного хранилища |
| `artifact-storage` | live, ready | провайдер хранения в памяти |

Разделение намеренное: внешние зависимости несут только тег `ready`, поэтому сбой Redis отводит трафик, не заставляя оркестратор уничтожать в остальном исправный контейнер. Резервные проверки in-memory несут оба тега, поскольку внешнего компонента для ожидания нет.

Обе пробы **анонимны**, поэтому пробы контейнера и оркестратора продолжают работать при включённой аутентификации. Это также означает, что формирование подробного ответа ограничено: детальный JSON по каждой проверке раскрывает имена классов реализации движков, например `ScribanDocumentGenerationEngine`, поэтому вне окружения Development пробы отвечают только общим статусом, если не задан параметр `DocumentProcessing:Api:ExposeHealthDetails`. Метод `HealthCheckResponseWriters.WriteMinimalUIResponse` является `internal` в ASP.NET Core, поэтому узел использует собственный формирователь краткого ответа.

1. Хорошее разделение ответственности.
2. Реальная подключаемая архитектура для движков.
3. Ясная модель расширяемости для форматов и парсеров.
4. Асинхронный поток уже близок к промышленному виду.
5. Наблюдаемость не отложена «на потом».
6. Проект базовой оценки производительности уже существует.
7. Логика автовыбора уменьшает связанность клиента.
8. Переключение инфраструктуры сохраняет простоту локальной разработки.
9. Решения, связанные с безопасностью, по умолчанию закрыты: ключ подписи не имеет значения в репозитории, поверхности для разработчиков включаются явно, а цели `api` нельзя переназначить из запроса.

## 8.2 Что уже ориентировано на промышленную эксплуатацию

- распространение идентификаторов корреляции;
- дедупликация;
- абстракция объектного хранилища;
- долговременное хранение задач с отправкой через Outbox;
- JWT-аутентификация с ролевой авторизацией;
- ограничения валидации запросов;
- асинхронная обработка на базе шины;
- разделение проверок liveness и readiness;
- метрики и трассировка;
- отказоустойчивый жизненный цикл генерации с предельными сроками повторов, окончательной отменой, возможностью отказа движка от повторов и предохранителем для внешних HTTP-зависимостей;
- хранение артефактов с ограниченным сроком и перевод покинутых задач в `Failed`;
- конвейер CI, который прерывает сборку при рекомендациях об уязвимостях NuGet;
- интеграционное покрытие основного поведения API, включая тесты провайдеров на контейнерах.

## 9. Текущие ограничения

Два ограничения, зафиксированные в предыдущих редакциях этого документа, **больше не соответствуют действительности** и сохранены здесь только для того, чтобы исправление было видимым: аутентификация и авторизация API *присутствуют* (JWT-bearer с ролевыми политиками), а долговременное реляционное хранилище задач *существует* (EF Core поверх PostgreSQL с миграциями под блокировкой advisory lock). Ниже приведён актуальный перечень.

Структурные:

1. Пока существует только один ограниченный контекст (bounded context).
2. Нет формальной стратегии версионирования контрактов движков.
3. Нет модели изоляции арендаторов.
4. Нет явных административных и эксплуатационных эндпоинтов помимо проверок работоспособности и статуса задач.

Обработка ресурсов:

5. Генерация **не является сквозной потоковой**. Оба пути HTTP-ответа передают свой поток в `Results.File`, а не копируют его в `byte[]`, однако каждый движок по-прежнему полностью материализует документ в памяти, а хранилище артефактов и кэш готовых документов хранят по полной копии. Передача запросов в base64 добавляет примерно 33 % сверху для двоичных входных данных. Любое утверждение о том, что «все движки используют потоковые подходы», неверно.
6. Ограничение размера — это защита на уровне запроса (10 МБ полезной нагрузки, 5 МБ шаблона), а не модель квот или регулирования допуска, поэтому совокупное потребление памяти при параллельной обработке не ограничено.

Устойчивость:

7. У клиентов Redis, RabbitMQ и MinIO нет явной политики повторов или предохранителя для каждого клиента; классифицируются и повторяются только сбои, проявившиеся в рабочем процессе генерации.
8. Отсутствуют изоляция (bulkhead) и ограничение частоты запросов для параллельной генерации.

Покрытие тестами и эксплуатация:

9. Redis и MinIO покрыты только на уровне адаптеров. Ни один тест не проводит один запрос через compose-стек со всеми четырьмя одновременно выбранными внешними провайдерами, хотя именно такая конфигурация и поставляется.
10. Compose по-прежнему экспортирует трассировки и метрики OpenTelemetry в консоль, что является разработческим выводом для стека, работающего в режиме Production.
11. Результаты бенчмарков не зафиксированы как базовый уровень в репозитории, поэтому сравнивать регрессии пока не с чем.

Принятый дефект:

12. На пути *с шаблоном* в MiniExcel плейсхолдер `{{placeholder}}`, привязанный к вложенному объекту или массиву, приводит к необработанному `IndexOutOfRangeException` внутри средства формирования MiniExcel. Это решение, а не упущение: отклонение вложенности сломало бы поддерживаемый синтаксис повторяющихся строк `{{items.field}}`, а различить эти два случая невозможно без разбора токенов шаблона книги. Три остальных охарактеризованных дефекта MiniExcel (зависимое от культуры форматирование чисел, молчаливая порча ячейки из-за вложенных значений, потеря заголовков при неровных массивах) исправлены.

`docs/improvement-plan.md`, раздел 11, ведёт учёт этих пунктов как пронумерованных задач с их текущим статусом.

## 10. Рекомендуемое направление развития архитектуры

В краткосрочной перспективе — сохранить модульный монолит.

Причины:

- текущий размер не оправдывает распределённую декомпозицию;
- границы становятся яснее, но всё ещё развиваются;
- единый развёртываемый модуль сохраняет скорость разработки.

В среднесрочной перспективе — развиваться в направлении:

- ~~выделенного долговременного хранения задач~~ — **выполнено** (EF Core + PostgreSQL, отправка через Outbox);
- ~~отдельного узла-воркера для фоновой генерации~~ — **выполнено** (`GenerateDocService.Worker`);
- ~~более строгого управления жизненным циклом артефактов~~ — **выполнено** (`ArtifactRetentionCleaner`, включая перевод покинутых задач в `Failed`);
- более строгой работы с конфигурацией и секретами — **частично выполнено**: ключ подписи не имеет значения по умолчанию в репозитории, а секреты целей `api` проверяются при запуске, однако хранилища секретов и механизма ротации по-прежнему нет, а compose экспортирует телеметрию в консоль;
- сквозной потоковой передачи, чтобы большому документу не требовались три полные копии в памяти (раздел 9, пункт 5);
- устойчивости для каждого клиента Redis, RabbitMQ и MinIO, а также изоляции или ограничения частоты запросов для параллельной генерации (раздел 9, пункты 7 и 8);
- изоляции и «песочницы» для движков, выполняющих рискованные преобразования, — теперь вопрос стал острее, поскольку движок `api` делегирует работу произвольным настроенным третьим сторонам.

В долгосрочной перспективе — разделять только те компоненты, которые оправдывают независимое масштабирование:

- шлюз API / точка входа;
- фоновые воркеры;
- ресурсоёмкие движки преобразования;
- конвейер отчётности и аналитики.

## 11.2 Диаграмма синхронной последовательности

```text
Client -> Correlation -> Auth -> Validation -> SyncDocumentGenerationService -> EngineRegistry -> Engine -> ParserRegistry/TemplateCache -> Metrics -> Results.File -> Client
```

Повторы отсутствуют: вызывающая сторона получает сбой и сама решает, отправлять запрос повторно.

## 11.3 Диаграмма асинхронной последовательности

```text
Client -> Correlation -> Auth -> Validation -> AsyncDocumentGenerationService -> DedupStore -> TaskRepository(+outbox) -> 202 Accepted
OutboxDispatcher -> lease -> MassTransit Send(queue) -> clear payload   [retry w/ backoff; Failed after the attempt limit]
Bus -> Worker -> BackgroundDocumentGenerationProcessor
                   -> load task, mark Processing (once)
                   -> generated-document cache lookup by fingerprint
                   -> on miss: resolve engine, generate, save artifact, update cache
                   -> attempt loop bounded by MaxAttempts under ProcessingTimeoutSeconds
                        TransientFailureClassifier: NonRetryable > Cancellation > transient type
                   -> mark Completed or Failed, record metrics once
                   -> publish DocumentGenerated or DocumentGenerationFailed once
Client -> TaskStatus API -> Download API
ArtifactRetentionCleaner (scheduled) -> delete expired artifacts/records; fail tasks stuck in Processing
```

## 12. Заключение

Проект находится в устойчивом промежуточном состоянии:

- зрелее, чем заготовка;
- всё ещё достаточно прост, чтобы развиваться безопасно;
- архитектурно пригоден для итеративного ужесточения требований.

Персистентность, аутентификация, валидация и устойчивость генерации — первая фаза плана улучшений — завершены, поэтому оставшаяся работа касается уже не корректности сервиса, а его экономичности под нагрузкой и наблюдаемости в эксплуатации: сквозная потоковая передача, устойчивость для каждого клиента, ограничения параллельности, сквозной тест compose-стека и зафиксированный базовый уровень производительности.

Наилучшие следующие шаги — не переписывание, а целевые улучшения в обработке ресурсов, эксплуатационной зрелости и управлении.
