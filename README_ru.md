# GenerateDocService

## Обзор

Базовая структура (скаффолд), построенная по принципам «чистой архитектуры» (Clean Architecture) для высоконагруженного сервиса генерации и преобразования документов на платформе .NET.

Текущая первая итерация включает:

- структуру решения и проектов, разделенную на уровни: Domain, Application, Infrastructure, Presentation, Host и Client;
- абстракции для механизмов генерации (движков);
- первый полноценный модуль на базе шаблонизатора Scriban;
- второй модуль на базе шаблонизатора DotLiquid;
- заготовку для модуля генерации PDF с использованием QuestPDF;
- интеграцию с внешним HTTP-сервисом для преобразования XSL-FO в PDF (совместимо с Apache FOP);
- реестр парсеров шаблонов с возможностью подключения новых провайдеров;
- базовый механизм кэширования скомпилированных шаблонов в оперативной памяти;
- поддержку кэширования скомпилированных шаблонов с использованием Redis;
- реестр движков и репозиторий задач, управляемые метаданными;
- автоматический выбор движка на основе его возможностей и приоритета (если конкретный движок не указан явно);
- контракты для асинхронного обмена сообщениями и инфраструктуру фоновой обработки на базе MassTransit;
- абстракции для дедупликации и кэширования созданных документов (в памяти, с возможностью последующего переноса в Redis);
- инфраструктурные настройки для кэширования/дедупликации (через Redis) и объектного хранилища;
- адаптер для объектного хранилища MinIO и локальную среду запуска через Docker Compose;
- проверки работоспособности (health checks: liveness и readiness) для движков и инфраструктурных зависимостей;
- промежуточное ПО (middleware) для работы с идентификаторами корреляции (correlation ID) в HTTP-запросах и при асинхронной обработке;
- логирование в консоль через Serilog с включением идентификаторов корреляции;
- трассировку OpenTelemetry для ASP.NET Core, исходящих HTTP-запросов и операций в MassTransit;
- пользовательские метрики OpenTelemetry для синхронных и асинхронных запросов, включая показатели успешности/ошибок и длительности генерации;
- метаданные OpenAPI для существующих эндпоинтов;
- демонстрационный («фиктивный») движок генерации;
- синхронные и асинхронные HTTP-эндпоинты;
- пример клиентского приложения на .NET;
- проект для оценки производительности (performance baseline) на базе NBomber;
- покрытие модульными (unit) и интеграционными тестами.

## Краткий обзор архитектуры

`GenerateDocService` представляет собой модульный монолит, построенный на принципе четкого разделения ответственности (separation of concerns):

- `src/Host/GenerateDocService.Api` — уровень, предоставляющий HTTP-интерфейс, аутентификацию, поддержку идентификаторов корреляции, проверки работоспособности, интеграцию с OpenTelemetry и API-контракты. - `src/Modules/DocumentProcessing/GenerateDocService.DocumentProcessing.Application` отвечает за оркестрацию, выбор механизма генерации (движка), управление жизненным циклом задач, дедупликацию и рабочие процессы создания документов.
- `src/Modules/DocumentProcessing/GenerateDocService.DocumentProcessing.Infrastructure` обеспечивает интеграцию с кэшами, хранилищами данных, механизмом Outbox, системами обмена сообщениями, объектным хранилищем (MinIO) и выполняет проверки работоспособности (health checks) инфраструктурных компонентов.
- `src/Modules/DocumentProcessing/GenerateDocService.DocumentProcessing.Presentation` выполняет преобразование моделей HTTP-запросов и ответов, поддерживая минималистичный уровень API.
- Модули `src/Engines/*` реализуют подключаемые (plugin-style) механизмы генерации документов. Их возможности определяются через метаданные, что позволяет системе маршрутизировать запросы динамически, без жесткой привязки к конкретным реализациям.
- `src/Host/GenerateDocService.Worker` отвечает за асинхронную генерацию документов, позволяя вынести трудоемкие операции за пределы основного пути обработки HTTP-запросов.

Такой подход упрощает локальный запуск решения, при этом позволяя легко заменить встроенные (in-memory) компоненты на полноценные системы — Redis, RabbitMQ, MinIO и PostgreSQL — без изменения основных контрактов приложения.

## Отказоустойчивость и надежность

Отказоустойчивость заложена в архитектуру сервиса изначально, а не добавлена ​​как второстепенная функция:

- Асинхронная генерация использует модель надежных задач (durable tasks) и паттерн Outbox, что предотвращает потерю запросов при перезапуске API или воркера.
- В случае временных сбоев (брокера сообщений, Redis или самого процесса генерации) предусмотрены повторные попытки с ограничением по времени (backoff) и установленным предельным сроком выполнения, что исключает бесконечные циклы повторов.
- Конвертер FOP (HTTP-сервис) защищен стандартным механизмом обеспечения устойчивости: с таймаутами для каждой попытки и общим ограничением времени выполнения, экспоненциальной задержкой между повторами и паттерном «предохранитель» (circuit breaker).
- Механизмы дедупликации и кэширования готовых документов предотвращают выполнение избыточной работы: если для заданного набора входных данных (отпечатка полезной нагрузки) документ уже был создан, повторная генерация не выполняется.
- Для in-memory провайдеров установлены ограничения по времени жизни (TTL) и объему данных, что предотвращает их бесконтрольный рост под нагрузкой.
- Проверки работоспособности (health checks и readiness probes) позволяют выявлять проблемы в инфраструктуре или движках генерации до того, как они приведут к сбоям, заметным для конечных пользователей.

Таким образом, проект спроектирован с учетом удобства разработки и надежности в промышленной эксплуатации, сохраняя при этом модульность, достаточную для последующего перехода к более распределенной модели развертывания. ## Документация
